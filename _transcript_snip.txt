## Анализ текущего проекта

Проект — **FastAPI + Jinja2 + vanilla JS**, не React. Модули: **Экономист**, **Секретарь**, **Юрист**. Отдельного `/frontend` и `/backend` нет — всё в одном репозитории `~/AI_DID`.

| Компонент из ТЗ | Что есть сейчас | Разрыв |
|----------------|-----------------|--------|
| Лист «Закупка 223-ФЗ» | Нет | Новый роутер + шаблон + JS + пункт nav |
| Роль «Специалист по закупкам» | Нет auth вообще | Cookie `did_sid` только для истории |
| Celery + Redis | Нет | Синхронная обработка (как у Юриста) |
| PostgreSQL / pgvector | Нет | ChromaDB + файлы на диске |
| RAG | `lawyer/rag.py` | Переиспользовать паттерн, **отдельная коллекция** |
| DOCX-парсер разделов | Только `paragraphs` в `doc_processor` | Нужен **новый** `parser.py` (Heading 1–3) |
| Markdown-рендер | Нет библиотеки | Нужен `markdown` / `mistune` на backend или простой JS |
| PDF/DOCX/TXT upload | Есть у Юриста | Адаптировать для БЗ закупок |

**Вывод:** блок «Закупка» — это **новый модуль** (~15–20 файлов), встроенный по образцу Юриста, но с двумя режимами, отдельной БЗ, парсером единого DOCX и (опционально) фоновыми задачами.

### Фаза 1 — Парсер + кэш документации (2–3 дня)

**`procurement/services/parser.py`**

```
Единый DOCX → {
  audit_id: uuid,
  file_hash: sha256,
  sections: {
    info_card: { text, pages[] },
    tz: { ... },
    contract: { ... },
    appendices: [{ name, text, pages }]
  },
  missing_sections: ["contract"],  # → 🔴
  parsed_at: datetime
}
```

**Логика разбиения:**
1. `python-docx`: стили `Heading 1/2/3`, нумерация
2. Ключевые фразы: «ИНФОРМАЦИОННАЯ КАРТА», «ТЕХНИЧЕСКОЕ ЗАДАНИЕ», «ПРОЕКТ ДОГОВОРА»
3. Fallback: `get_llm()` — «определи границы разделов» (только если заголовки не найдены)
4. **Положение о закупке не ищем** в этом файле

**Кэш (без Redis на старте):**
- `procurement/cache/{file_hash}.json` + метаданные в `procurement/cache/index.json`
- TTL 24 ч (env `PROCUREMENT_CACHE_TTL_HOURS=24`)
- Оба режима читают один кэш по `audit_id`

**Endpoint:**
- `POST /api/procurement-audit/upload` — upload DOCX → parse → cache → `{ audit_id, sections_detected, missing_sections }`

### Фаза 3 — Режим А: проверка документации (4–5 дней)

**`procurement/services/`**

| Модуль | Тип | Назначение |
|--------|-----|------------|
| `cross_checker.py` | Детерминированный | НМЦД, предмет, способ, сроки, обеспечение |
| `plagiarism_scanner.py` | Детерминированный + regex | Copy-paste, чужие ИНН, неверные способы |
| `fz223_validator.py` | Правила + RAG | 223-ФЗ, **только ПП РФ № 1875** (не 925) |
| `contract_reviewer.py` | Правила + LLM точечно | ГК РФ, существенные условия |
| `llm_orchestrator.py` | LLM по чанкам | Семантика там, где код не справляется |
| `report_generator.py` | Export | JSON → PDF/DOCX |

**Поток:**
```
POST /api/procurement-audit/{audit_id}/check
  → загрузка cached sections
  → cross_checker + plagiarism (параллельно, asyncio)
  → fz223_validator (+ RAG по БЗ если есть Положение)
  → contract_reviewer
  → агрегация issues[] → verdict
  → сохранение report в procurement/cache/{audit_id}_check.json
```

**Статус (без Celery v1):**
- In-memory / JSON: `{ status: pending|running|done|error, progress: 0-100, step: "cross_check" }`
- `GET /api/procurement-audit/{audit_id}/status?mode=check` — polling каждые 2 с
- **Celery v2:** те же шаги в `@celery.task`, Redis как broker

**Если Положения нет в БЗ:** 🟡 issue `position_compliance` + пропуск шага 3 по Положению.
